# `test-data-seeder` — Method

> Reference doc for `test-data-seeder`. The agent body keeps the role,
> when-to-invoke, inputs, output format, and quality criteria. The
> detailed 7-step method lives here and is read on demand at the start
> of an invocation.

## Step 1 — Detect the migration tool and the seed-injection point

Probe the backend in this order; stop at the first match.

| Detect | If found |
|---|---|
| `src/main/resources/db/changelog/db.changelog-master.yaml` (or `.xml`) | **Liquibase** — write a YAML changeset file gated `context: test` (or whatever non-prod context the project already uses), register it in `db.changelog-master.{yaml,xml}`. |
| `src/main/resources/db/migration/V*.sql` | **Flyway** — write a versioned migration `V<next>__seed_test_data.sql`; use a profile-gated SQL guard if Flyway placeholders are configured, otherwise emit it under a `db/migration/test/` location wired only in the test/dev profile. |
| `manage.py` + `fixtures/` | **Django fixtures** — write a JSON / YAML fixture loaded by `loaddata` in the dev/test settings. |
| `db/seeds.rb` or `db/seeds/development.rb` | **Rails seeds** — append idempotent `find_or_create_by!` blocks. |
| `Migrations/` with `*.Designer.cs` or `dbContext.HasData()` | **EF Core Data Seeding** — extend `OnModelCreating` with `modelBuilder.Entity<…>().HasData(…)` gated by environment, or write a new migration with seed `InsertData` ops. |
| `knexfile.{js,ts}` + `seeds/` | **Knex seeds** — write `<NN>_<topic>.{js,ts}` with `knex(...).insert(...)` patterns. |
| `data-source.ts` with TypeORM | **TypeORM seeders** (or `typeorm-seeding` if installed). |
| `migrations/*.sql` only (no tool) | **Raw SQL fallback** — write `<NN>__seed_test_data.sql` next to existing migrations and document how to invoke it. |
| None of the above | Halt and ask the supervisor which seed mechanism to use; do not invent one. |

Record the chosen tool in the dataset plan (see Step 3) so the
restart command in Step 6 can be picked correctly.

## Step 2 — Discover the schema and the dataset envelope

Read the schema, not the README. From the migration files and the
ORM entity classes / model files, extract for every table that will
receive seed data:

- table name (and schema/namespace if any)
- column name, type, length, nullable, default
- primary key (composite or auto-generated)
- foreign keys (table, column, on-delete behavior)
- unique constraints
- check constraints (enum-like CHECK lists)
- whether the PK is auto-generated by the DB (so you can omit it on
  insert) or manually assigned (so you must compute non-colliding values)

In parallel, read `docs/analysis/01-functional/` for:

- the actor list (drives the login-user spread)
- the use-case list (drives lifecycle-state coverage)
- the bounded-context map (drives the cross-module pivot graph)
- the enum / state lists (drives column-value enumeration)

Cross-reference: every column you intend to fill must be reachable
from at least one Phase 1 element. If a column has no functional
mapping, fill it with a sentinel that is valid for the column type
(empty string, `null` if nullable, `false`, `0`) and document the
deviation in the dataset-plan output.

## Step 3 — Design the dataset (call the design skill)

Invoke `test-data-design-standards` and apply its rules. Produce, as
an internal artifact, a **dataset plan** containing:

1. **Pivot entities (5 by default).** A small set of core domain
   entities (customers, orders, users, accounts — whatever the
   bounded contexts are about) used as anchors across every module.
   Every other table that has a FK to one of these tables references
   one of these IDs.
2. **Login-user spread.** At least one admin user, one
   single-permission user, one multi-permission user, one inactive /
   locked user (where the schema supports it).
3. **Lifecycle-state coverage.** For every entity that has a status
   / state column, seed at least one row per state. For state
   machines, seed at least one row at every reachable state. Use
   Phase 1 state lists; do not invent states.
4. **Edge / boundary realism.** At least one row at each numeric
   boundary the schema enforces (max-length string, 0, very large /
   very small numeric, near-future / near-past date).
5. **Cross-module coherence map.** A short table showing how the
   pivot IDs flow through every module: pivot entity → module → row
   count → which fields tie back to which pivot ID.

Validate the plan against the **constraints**:

- Every FK has a target row.
- No string exceeds its column's declared length (check VARCHAR(N)
  for every textual value you plan to insert; this is the most
  common seed failure).
- Every NOT NULL column has a value.
- Every UNIQUE constraint is respected.
- Every CHECK constraint is satisfied.
- Composite PKs do not collide with other rows.

## Step 4 — Write the seed file(s)

Generate the seed in the tool's native format (call
`database-migration-patterns` for the exact templates). Apply these
discipline rules regardless of tool:

- **Idempotent header.** The file must be safe to apply once and only
  once. For tools without built-in idempotence (raw SQL, Rails), use
  `INSERT ... ON CONFLICT DO NOTHING` (Postgres / SQLite),
  `MERGE ... WHEN NOT MATCHED` (SQL Server / Oracle), or
  `find_or_create_by!` (Rails).
- **Non-prod gating.** Use the project's own profile mechanism:
  Liquibase `context: test`, Flyway folder split + profile, Django
  `--settings`, Rails `Rails.env`, EF environment check, Knex
  per-env folder. The file MUST NOT execute in `prod`.
- **Stable identifiers.** Where the schema lets you assign IDs
  manually, use a documented numeric base (`1001`, `1002`, …) or
  business-keyed IDs (`COMPANY-001`, …) so other test fixtures can
  reference them.
- **Lookup-first FKs.** For FKs that point to auto-generated PKs,
  use `INSERT ... SELECT` patterns or the tool's native ID-lookup
  to resolve the parent ID at insertion time. Never hardcode an
  auto-generated ID.
- **Ordering by dependency.** Group changesets / SQL statements so
  parents are inserted before children. The dataset plan's coherence
  map is the topological order.
- **Length safety.** Before emitting any string literal, verify it
  is ≤ the declared column length. Common gotcha: a free-text
  comment exceeds a 10-char status column. Use the column-length
  pass from `database-migration-patterns` as a final check.
- **Single file vs many.** Default to one file per bounded context
  with a clear `<NN>-<bc>-seed` numbering. If the project already
  has a one-file convention, follow it.

Write the file(s) into the project's existing seed / migration
directory tree — never invent a new location.

## Step 5 — Wire any required auth-store extensions

If the backend has an in-memory auth / user store (common in
test / dev profiles for Spring Boot + Spring Security demo apps,
Django dev settings, FastAPI tutorial templates, Express
demo middleware), extend it to include the seeded login users so
the user can actually log in and click around.

This is the **only** TO-BE source edit you may perform. Rules:

- Add users only — never remove or change existing ones.
- Match passwords to a documented test value (e.g. `password ==
  username`) so the supervisor's recap can publish credentials.
- Use the project's existing hashing function (do not introduce a
  new one).
- Keep the change in a clearly test-gated file (`@Profile("test")`
  / `if settings.DEBUG:` / `if (NODE_ENV !== 'production')` /
  equivalent).

If the project uses a real user table (DB-backed auth, OAuth, SSO),
seed the user rows in the seed file instead and skip this step.

## Step 6 — Restart and verify (when execution policy allows)

When `execute_policy` is `auto` (and the tooling is reachable) or
`on`:

1. Stop any currently-running instance of the backend that holds the
   migration lock (`ps` / `netstat` / `lsof` / `Get-Process` —
   whichever is appropriate for the OS).
2. Restart the backend with the test / dev profile that activates
   the seed (the tool detected in Step 1 dictates the command).
3. Wait for `Started`/`Ready`/`Listening on` in the log; cap the wait
   at a sensible bound and surface a timeout error if it never
   appears.
4. Run **API smoke calls** against 3–5 representative endpoints
   covering different bounded contexts. Use the project's OpenAPI
   contract from `docs/refactoring/` to pick endpoints. Verify each
   returns a non-empty result that references the pivot entities.
5. If the supervisor passes a list of "must-not-be-empty" endpoints
   (from the UI smoke routes), verify each of those too.

When `execute_policy` is `off`, skip Step 6 and emit a Step 6
checklist in the recap so the supervisor can run it manually or
defer to Step 6.1 of the UI smoke gate.

## Step 7 — Recap to the supervisor

Return a single recap message in the format defined under "Output
format" in the agent body. The supervisor uses it to decide whether
to proceed to Step 6 or to redispatch.
